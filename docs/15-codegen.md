# LLVM Compilation

Kryos can run code two ways: interpreted (with self-healing error recovery) or compiled to a native binary through LLVM. This chapter covers the compilation pipeline, what gets compiled, how to build and debug, and what happens under the hood.

## The Pipeline

Source code goes through six stages to become a native binary:

```
.kry source
    |
    v
  Lexer        tokenize()       -> token stream
    |
    v
  Parser       parse()          -> AST (abstract syntax tree)
    |
    v
  Ownership    ownership check  -> verified ownership/borrowing
    |
    v
  Comptime     comptime eval    -> compile-time values embedded
    |
    v
  Type Check   type inference   -> type-annotated AST
    |
    v
  Codegen      CodeGenerator    -> LLVM IR text (.ll file)
    |
    v
  llc                          -> object file (.o)
    |
    v
  clang                        -> native binary (executable)
```

The first five stages run inside the Kryos compiler (pure Python). The last two stages shell out to the LLVM toolchain -- you need `llc` and `clang` installed on your system.

## Building a Program

```bash
kryos build hello.kry
```

This runs the full pipeline and produces an executable. By default, the output is named `a.out` (or `a.exe` on Windows).

Under the hood, `kryos build` does:

1. Reads and lexes the `.kry` source
2. Parses into an AST
3. Runs ownership checking
4. Evaluates `comptime` blocks
5. Type-checks the AST
6. Generates LLVM IR text
7. Writes the IR to a temp file (`input.ll`)
8. Runs `llc -filetype=obj input.ll -o input.o` to produce an object file
9. Runs `clang input.o -o a.out` to link into a native binary

If `llc` or `clang` are not found on your PATH, the build fails with a descriptive message:

```
llc not found -- install LLVM to compile to native code
clang not found -- install LLVM/Clang to link the binary
```

### Viewing the Generated IR

To inspect the LLVM IR without compiling to a binary:

```bash
kryos build hello.kry --emit-ir
```

This writes the `.ll` file and prints it. Every generated module starts with:

```llvm
; Kryos LLVM IR -- generated by the Kryos compiler
; Module: <main>
target triple = "x86_64-pc-linux-gnu"
```

The target triple is set automatically based on your platform:
- Linux: `x86_64-pc-linux-gnu`
- macOS: `x86_64-apple-macosx10.15.0`
- Windows: `x86_64-pc-windows-msvc`

## Interpreted vs. Compiled

Not everything in Kryos compiles to LLVM IR. The language has two execution modes, and some features are only available in one.

### What Gets Compiled

The LLVM codegen handles the core language:

| Feature | Status |
|---------|--------|
| Functions (`fn`) | Compiled |
| Variables (`let`, `let mut`) | Compiled |
| Integer arithmetic (`+`, `-`, `*`, `/`, `%`) | Compiled |
| Float arithmetic | Compiled |
| Comparisons (`==`, `!=`, `<`, `>`, `<=`, `>=`) | Compiled |
| Boolean logic (`and`, `or`, `not`) | Compiled |
| Power operator (`**`) | Compiled (via `llvm.pow.f64`) |
| `if`/`elif`/`else` | Compiled |
| `while` loops | Compiled |
| `for x in range(start, end)` | Compiled |
| `break` and `continue` | Compiled |
| Strings and string concatenation (`+`) | Compiled (via malloc/strcpy/strcat) |
| `println()` and `print()` | Compiled (via puts/printf) |
| `len()`, `to_string()`, `sqrt()`, `abs()` | Compiled as builtins |
| `push()`, `pop()` | Compiled (dynamic array with realloc) |
| Structs and field access | Compiled |
| Enum types (simple and payload) | Compiled |
| `match` expressions | Compiled (via LLVM switch) |
| `impl` blocks and methods | Compiled |
| Lambda expressions | Compiled (as named functions) |
| Generics | Compiled (monomorphization) |
| Traits | Vtable type generation |
| Array literals | Compiled (heap-allocated with length/capacity/data) |

### What Stays Interpreted

The AI runtime and advanced features run in the interpreter:

| Feature | Why not compiled |
|---------|-----------------|
| Tensor operations | Uses numpy/Python backend |
| Agents | Requires dynamic dispatch and runtime memory |
| Probable<T> | Python dataclass machinery |
| Streams | Lazy evaluation with Python generators |
| Data lineage | Runtime tracking with metadata |
| Cost tracking | Runtime instrumentation |
| FFI (Python/C) | Python ctypes and importlib |
| Self-healing error recovery | Interpreter-level feature |
| Capability checking | Runtime enforcement |

This split is intentional. The core language compiles to fast native code. The AI runtime leverages Python's ecosystem for flexibility. As Kryos matures, more of the runtime will move to compiled code.

## How the Codegen Works

### Type Mapping

Kryos types map to LLVM IR types:

| Kryos | LLVM IR |
|-------|---------|
| `i8` | `i8` |
| `i16` | `i16` |
| `i32` | `i32` |
| `i64` | `i64` |
| `i128` | `i128` |
| `u8` - `u128` | Same as signed (LLVM does not distinguish) |
| `f32` | `float` |
| `f64` | `double` |
| `bool` | `i1` |
| `str` | `i8*` |
| `char` | `i8` |
| `void` | `void` |

### Functions

Each `fn` declaration becomes an LLVM `define`. Parameters are allocated on the stack and stored, then the body is generated.

```
fn add(a: i32, b: i32) -> i32 {
    return a + b
}
```

Generates:

```llvm
define i32 @add(i32 %a, i32 %b) {
entry:
  %0 = alloca i32
  store i32 %a, i32* %0
  %1 = alloca i32
  store i32 %b, i32* %1
  %2 = load i32, i32* %0
  %3 = load i32, i32* %1
  %4 = add i32 %2, %3
  ret i32 %4
}
```

### Top-Level Statements

Statements outside of any function are wrapped in a `main()` function automatically. This is why a Kryos program like:

```
println("Hello!")
```

Works without explicitly defining `main()`. The codegen wraps it as:

```llvm
define i32 @main() {
entry:
  ; ... println code ...
  ret i32 0
}
```

If your program defines its own `fn main()`, that takes precedence.

### Strings

String literals become global constants. String concatenation with `+` compiles to `strlen` + `malloc` + `strcpy` + `strcat`, allocating a new buffer for each concatenation.

```
let greeting = "Hello, " + name
```

This generates calls to four C standard library functions. The runtime declares them as externs:

```llvm
declare i64 @strlen(i8*)
declare i8* @malloc(i64)
declare i8* @strcpy(i8*, i8*)
declare i8* @strcat(i8*, i8*)
```

### Arrays

Array literals compile to a heap-allocated struct with three fields:

```llvm
%Array_i32 = type { i32, i32, i32* }
;                   ^     ^     ^
;                   |     |     data pointer
;                   |     capacity
;                   length
```

`push()` checks if `length == capacity`, doubles the capacity via `realloc` if needed, stores the new element, and increments the length. This is the same growth strategy as `std::vector` in C++.

### Control Flow

**`if`/`elif`/`else`** compiles to conditional branches:

```llvm
br i1 %cond, label %if.then, label %if.else
```

**`while` loops** use a condition block, body block, and end block:

```llvm
while.cond:
  ; evaluate condition
  br i1 %cmp, label %while.body, label %while.end
while.body:
  ; body
  br label %while.cond
while.end:
```

**`for x in range(start, end)`** compiles to a counter-based loop with an alloca for the loop variable, a condition block (`icmp slt`), a body block, and an increment block:

```llvm
for.cond:
  %cur = load i32, i32* %counter
  %cmp = icmp slt i32 %cur, %end
  br i1 %cmp, label %for.body, label %for.end
for.body:
  ; body
  br label %for.inc
for.inc:
  %inc = add i32 %cur, 1
  store i32 %inc, i32* %counter
  br label %for.cond
for.end:
```

### Structs

Struct declarations become LLVM named struct types:

```
struct Point {
    x: i32,
    y: i32
}
```

```llvm
%struct.Point = type { i32, i32 }
```

Field access uses `getelementptr` with the field index.

### Enums

Simple enums (no payload) compile to a tag-only struct:

```
enum Direction { North, South, East, West }
```

```llvm
%enum.Direction = type { i8 }
```

Enums with payload variants get a tag byte plus a byte array large enough to hold the largest variant:

```
enum Shape { Circle(f64), Rect(f64, f64) }
```

```llvm
%enum.Shape = type { i8, [16 x i8] }
```

The `match` expression on enums compiles to an LLVM `switch` instruction that dispatches on the tag value.

### Impl Blocks and Methods

Methods in `impl` blocks are compiled as regular functions with a mangled name: `TypeName_methodName`. The `self` parameter becomes a pointer to the struct.

```
impl Point {
    fn get_x(self) -> i32 {
        return self.x
    }
}
```

Compiles as:

```llvm
define i32 @Point_get_x(%struct.Point* %self) {
  ; ...
}
```

A method call `p.get_x()` compiles to `call i32 @Point_get_x(%struct.Point* %p_ptr)`.

### Lambda Expressions

Lambdas are lifted to top-level functions with generated names (`__lambda_0`, `__lambda_1`, etc.):

```
let f = |x: i32| -> i32 { return x * 2 }
```

Generates:

```llvm
define i32 @__lambda_0(i32 %x) {
entry:
  ; ... body ...
}
```

The variable `f` holds a function pointer.

### Generics (Monomorphization)

Generic functions are compiled by monomorphization -- each unique combination of type arguments produces a specialized copy of the function. The mangled name includes the concrete types:

```
fn identity<T>(x: T) -> T {
    return x
}

// Called as identity<i32>(42) -> compiles as identity_i32
// Called as identity<f64>(3.14) -> compiles as identity_f64
```

Each specialization is generated at most once and cached.

### Traits

Trait declarations generate a vtable struct type:

```
trait Drawable {
    fn draw(self) -> void
}
```

```llvm
%vtable.Drawable = type { ... }
```

This lays the groundwork for dynamic dispatch.

## Debugging Compiled Output

### Reading the IR

LLVM IR is verbose but straightforward. Key things to look for:

- **`define`** -- function definitions
- **`entry:`** -- every function starts here
- **`alloca`** -- stack allocation for a local variable
- **`store`/`load`** -- write to / read from a stack slot
- **`add`/`sub`/`mul`/`sdiv`** -- integer arithmetic
- **`fadd`/`fsub`/`fmul`/`fdiv`** -- float arithmetic
- **`icmp`/`fcmp`** -- integer/float comparisons
- **`br`** -- branch (conditional or unconditional)
- **`call`** -- function call
- **`ret`** -- return from function
- **`getelementptr`** -- struct/array field access
- **`phi`** -- SSA merge point (used in loops and branches)

### Common Issues

**"llc not found"** -- Install LLVM. On Ubuntu: `apt install llvm`. On macOS: `brew install llvm`. On Windows: install LLVM from the releases page and add to PATH.

**"clang not found"** -- Install Clang. Usually comes with LLVM.

**"llc failed"** -- The generated IR has an error. Use `--emit-ir` to inspect it. Common causes: type mismatches, missing terminators, undeclared externs.

**"clang failed"** -- The object file compiled but linking failed. Usually means a missing library (e.g., you called `puts` but libc is not linked). On most systems, clang links libc by default.

### Verifying the IR

You can run `lli` (LLVM's IR interpreter) to test the generated IR without compiling to native:

```bash
lli output.ll
```

This is useful for quick iteration -- no need to wait for the full compile cycle.

## What Compiles vs. What Runs

A practical rule of thumb:

- **Core language** (variables, functions, control flow, structs, enums, arrays, strings, math) -- **compiles** to fast native code
- **AI runtime** (tensors, agents, probability, streams, lineage, cost) -- **interpreted** through the Python runtime
- **FFI** -- **interpreted** (Python's ctypes/importlib)
- **Self-healing** -- **interpreted** (requires runtime error interception)

When you run `kryos run file.kry`, everything goes through the interpreter. When you run `kryos build file.kry`, only the compilable subset produces a native binary. If your code uses AI runtime features, run it with `kryos run`; if it is pure computation, `kryos build` gives you native speed.
