# Modules and Packages

> **Implementation Status:** The `use` statement is parsed and module resolution (sibling files, `src/` directory, directory modules) is implemented in the compiler. The package manager CLI commands (`kryos init`, `kryos add`, `kryos remove`, `kryos install`, `kryos publish`) are implemented. Cross-module name resolution (importing functions/types from other files into the caller's scope) is partially working -- simple cases work but complex cross-file references may fail. Extern imports (`use extern "c" ...`, `use extern "rust" ...`) are parsed but the foreign FFI bridge is not yet wired.

Kryos projects are organized around modules (individual `.kry` files) and packages (collections of modules with a manifest). The module system uses `use` statements to bring code from other files and packages into scope, and the package manager handles dependency resolution, versioning, and publishing.

## The `use` Statement

Import code from other modules with `use`. Paths use `::` as the separator.

```
// Import a module from your project's src/ directory
use math_utils

// Import a submodule (src/ml/transformers.kry)
use ml::transformers

// Import with an alias
use ml::transformers as tf

// Import from an external (non-Kryos) source
use extern "c" libsodium
```

### Resolution Order

When Kryos encounters `use foo::bar`, it searches in this order:

1. **Project-local** -- `src/foo/bar.kry` in your project directory
2. **Directory module** -- `src/foo/bar/mod.kry` (if `bar` is a directory)
3. **Installed packages** -- `~/.kryos/packages/foo/<latest-version>/src/bar.kry`

For a single-segment import like `use utils`, Kryos checks `src/utils.kry` first, then `src/utils/mod.kry`, then installed packages.

### Extern Imports

The `use extern` syntax imports modules from foreign ecosystems (C, Rust). The string after `extern` identifies the source system:

```
use extern "c" libsodium
use extern "rust" serde
```

These imports require the `ffi` capability in your `kryos.toml` and the corresponding foreign dependency declared under `[dependencies.c]` or `[dependencies.rust]`.

## Project Structure

A standard Kryos project looks like this:

```
my-project/
  kryos.toml          # Package manifest
  src/
    main.kry           # Entry point
    utils.kry           # A module (imported as `use utils`)
    ml/
      mod.kry           # Directory module (imported as `use ml`)
      transformers.kry  # Submodule (imported as `use ml::transformers`)
```

Running `kryos init` creates this structure automatically with a starter `main.kry`:

```
// Generated by kryos init
fn main() {
    print("Hello from Kryos!")
}

main()
```

## Package Manifest: `kryos.toml`

Every Kryos project has a `kryos.toml` at its root. This is a TOML file that defines the package metadata, dependencies, build settings, and capability permissions.

### Default Manifest

When you run `kryos init`, you get:

```toml
[package]
name = "my-project"
version = "0.1.0"
description = ""
authors = []
license = "MIT"
kryos_version = ">=0.1.0"

[dependencies]

[build]
target = "native"
optimization = "release"

[capabilities]
allowed = ["compute"]
```

### Sections

**`[package]`** -- Package identity and metadata.

| Field | Description |
|-------|-------------|
| `name` | Package name (used in `use` imports and the registry) |
| `version` | Semantic version string (major.minor.patch) |
| `description` | One-line description |
| `authors` | List of author strings |
| `license` | SPDX license identifier |
| `kryos_version` | Minimum Kryos version constraint |

**`[dependencies]`** -- Top-level entries are Kryos package dependencies. Foreign dependencies go in sub-tables.

```toml
[dependencies]
kryos_ml = "^1.0"
data_utils = ">=0.5.0"

[dependencies.c]
libsodium = "1.0.18"

[dependencies.rust]
serde = "1.0"
```

**`[build]`** -- Compilation settings.

| Field | Description |
|-------|-------------|
| `target` | Compilation target: `"native"`, `"wasm"`, etc. |
| `optimization` | `"debug"` or `"release"` |

**`[capabilities]`** -- Which capabilities this package is allowed to use. Kryos is deny-by-default; if your code calls network functions without `net` in the allowed list, it fails.

```toml
[capabilities]
allowed = ["compute", "fs", "net", "ffi"]
```

## Package Manager Commands

Kryos has a built-in package manager accessible through the `kryos` CLI.

### `kryos init`

Create a new project in the current directory (or a specified path).

```bash
# Initialize in the current directory
kryos init

# Initialize in a new directory with a custom name
kryos init ./my-app --name my-app
```

This creates:
- `kryos.toml` with default config
- `src/` directory
- `src/main.kry` starter file

If a `kryos.toml` already exists, it reports that the project is already initialized.

### `kryos add`

Add a dependency to `kryos.toml`.

```bash
# Add a Kryos package (any version)
kryos add data_utils

# Add with a version constraint
kryos add kryos_ml "^1.0"

# Add a C library
kryos add libsodium "1.0.18" --category c

# Add a Rust crate
kryos add serde "1.0" --category rust
```

The dependency is written directly into `kryos.toml` under the appropriate section. For Kryos packages, it goes under `[dependencies]`. For foreign dependencies, it goes under `[dependencies.c]` or `[dependencies.rust]`.

### `kryos remove`

Remove a dependency from `kryos.toml`.

```bash
kryos remove data_utils

# Remove a foreign dependency
kryos remove libsodium --category c
```

If the package is not found in the manifest, it reports that the dependency was not found. Empty foreign sub-tables are cleaned up automatically.

### `kryos install`

Resolve and install all dependencies listed in `kryos.toml`.

```bash
kryos install
```

For Kryos packages, the manager looks in the local registry (`~/.kryos/packages/`) for versions that satisfy the constraint. It reports the status of each dependency:

```
  [OK]      data_utils = 1.2.0
  [MISSING] kryos_ml -- not found in local registry
  [c]       ensure libsodium 1.0.18 is available on system
  [rust]    ensure serde 1.0 is available via cargo
```

Foreign dependencies are not auto-installed. The manager prints the command you need to run so you can install them with the appropriate tool.

### `kryos publish`

Publish the current project to the local package registry.

```bash
kryos publish
```

This copies `kryos.toml` and the `src/` directory into `~/.kryos/packages/<name>/<version>/`. Other projects on the same machine can then depend on this package.

The `[package]` section in `kryos.toml` must have a `name` set.

## Semver Resolution

Kryos uses semantic versioning for all package constraints. The following constraint formats are supported:

| Constraint | Meaning | Example |
|-----------|---------|---------|
| `"1.2.3"` | Exact match | Only version 1.2.3 |
| `"1.2"` | Major.minor match | Any 1.2.x |
| `"*"` | Any version | Whatever is available |
| `"^1.0"` | Compatible | Same major, >= 1.0 (i.e., 1.x.x where x >= 0) |
| `"~1.2"` | Approximate | Same major.minor, >= 1.2 (i.e., 1.2.x where x >= 0) |
| `">=1.0"` | Greater or equal | 1.0.0 and above |
| `"<=2.0"` | Less or equal | Up to 2.0.0 |
| `">1.0"` | Greater than | Strictly above 1.0.0 |
| `"<2.0"` | Less than | Strictly below 2.0.0 |

When multiple versions satisfy a constraint, Kryos selects the **highest matching version**. This follows the standard semver principle: prefer the latest compatible release.

### How Caret (`^`) Works

`^1.2.3` means "any version >= 1.2.3 with the same major version." So `^1.0` matches 1.0.0, 1.5.3, and 1.99.0, but not 2.0.0. This is the recommended default for most dependencies because it allows non-breaking updates while preventing major version surprises.

### How Tilde (`~`) Works

`~1.2.3` means "any version >= 1.2.3 with the same major.minor." So `~1.2` matches 1.2.0, 1.2.5, and 1.2.99, but not 1.3.0. Use this when you need tighter control over patch-level changes.

## Local Package Registry

All Kryos packages are stored in `~/.kryos/packages/`. The directory structure is:

```
~/.kryos/packages/
  data_utils/
    0.1.0/
      kryos.toml
      src/
        mod.kry
        parser.kry
    0.2.0/
      kryos.toml
      src/
        mod.kry
        parser.kry
  kryos_ml/
    1.0.0/
      ...
```

Each package has one directory per published version. When resolving `use data_utils::parser`, Kryos finds the latest version of `data_utils` that satisfies the constraint in your `kryos.toml`, then looks for `src/parser.kry` inside that version directory.

## Dependency Categories

Kryos supports four categories of dependencies:

| Category | Config key | What it does |
|----------|-----------|-------------|
| `kryos` | `[dependencies]` (top-level) | Native Kryos packages, resolved from local registry |
| `rust` | `[dependencies.rust]` | Rust crates, added via `cargo` |
| `c` | `[dependencies.c]` | C/C++ libraries, must be available on the system |

Foreign dependencies require the `ffi` capability and the appropriate FFI calls in your code (see the [FFI chapter](13-ffi.md)).

## Listing Dependencies

View all dependencies for a project:

```bash
kryos deps list
```

This shows dependencies grouped by category:

```
kryos:
  data_utils = "^1.0"
c:
  libsodium = "1.0.18"
rust:
  serde = "1.0"
```

## Practical Example

Here is a complete workflow for starting a project that uses both Kryos packages and C libraries:

```bash
# Create the project
kryos init my-secure-app --name my-secure-app
cd my-secure-app

# Add dependencies
kryos add data_utils "^0.2"
kryos add libsodium "1.0.18" --category c

# Install (resolves Kryos deps, prints system commands for foreign deps)
kryos install

# Edit kryos.toml to allow FFI
# [capabilities]
# allowed = ["compute", "ffi"]
```

Then in `src/main.kry`:

```
use data_utils::parser

fn main() {
    let data = parser::load("training_data.csv")
    println("Loaded " + to_string(len(data)) + " rows")
}

main()
```

Run it:

```bash
kryos run src/main.kry
```
