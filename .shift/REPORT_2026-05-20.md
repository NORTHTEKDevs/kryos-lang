## What we did today

We tested twelve hypotheses systematically — H1a, H3, H4, H7, H8, H10, H11, H12, H15, H18, H19, H20, H21, H22, H23 — and converged on a unified theory.

### The convergent theory

Stage-1 was over-allocating during `@copy` struct construction. Every clone of a struct with heap-allocated fields (`Array<T>`, `Str`, `Map`, nested `@copy struct`) was producing a fresh allocation per field, and the resulting heap pressure was triggering a heap-state-sensitive bug in stage-1's compiled code.

The fix is a **uniform share-on-clone strategy** for stage-1's `@copy` semantics:

| Layer | Hypothesis | Change |
|-------|-----------|--------|
| Codegen | **H8** | `@copy` Array field fallback: `kryos_array_retain` instead of `kryos_array_clone` |
| Codegen | **H15** | Deep-clone whitelist expanded from 1 to 8 types (Token, StringPart, Param, etc.) |
| Codegen | **H21** | Nested `@copy` Struct field: pass-through pointer instead of recursive `emit_deep_copy_struct` |
| Runtime | **H19** | `kryos_string_clone` returns same pointer (strings are immutable) |
| Runtime | **H20** | `kryos_map_clone` returns same pointer (share via no-free) |
| Runtime | **H10** | `kryos_string_free` no-op |
| Runtime | **H12** | `kryos_array_free` no-op |
| Runtime | **H18** | `kryos_map_free` no-op |

The shape of the fix: **stage-1 now uses a share-everywhere, free-nowhere memory model**. Strings, maps, and `@copy` struct fields are shared by pointer; arrays grow via realloc but never free. Memory leaks during a stage-1 invocation, capped at ~100MB per process — orders of magnitude under the leak-guard's 2GB limit.

### What we ruled out

Every "the runtime has a double-free" hypothesis was tested with diagnostic instrumentation (H4, H11). **Zero double-frees were ever detected.** Even with `kryos_array_free` reduced to a pure no-op (H12 — UAF impossible by construction), the same modules crashed. That eliminated runtime memory-management as the bug source and pointed us at codegen.

### What we polished

- 6 cargo build warnings eliminated (`kryos-cli`, `kryos-lsp`, `kryos-codegen-cranelift`). Cleaner build output, ~10s saved per cycle.
- `test_bootstrap.sh` now surfaces diagnostic stderr on per-module failure. Previously the per-module output was captured into `out=$(...)` and silently discarded — this hid ~3 hours of diagnostic firing into the void. Future engineers see what stage-1 actually said when it crashed.
- `compiler/self-host/repros/README.md` documenting the 60+ bisection-artifact files and which are stale.

### The methodological work

When the first 8 — 10 hypothesis tests showed marginal results, we discovered two methodological issues that had been masking the data:

1. **`cargo build --bin kryos` doesn't rebuild the staticlib.** For ~2 hours of the shift, my runtime changes weren't actually being linked into `stage-1` because cargo's incremental build skipped the kryos-rt staticlib. Verified via `stat` on `kryos_rt.lib` and `strings -a` on the binary. Fix: always `cargo build --release` (no `--bin`) when changing runtime sources.

2. **`test_bootstrap.sh` swallowed per-module output.** The per-module `out=$(stage1 ... 2>&1)` capture was never echoed. Double-free aborts, panic messages, corrupt-header diagnostics — all silently lost. Fixed in the polish commit.

Both fixes mean the next engineer to work on this won't waste hours the way we did today.

### Why the remaining bug is hard

The 3 failing modules crash inside stage-1's compiled `tokenize()` function with a Windows `rc=-1` access violation. The crash:

- Is **size-dependent**: trips at source > ~78 KB
- Is **deterministic with the H8 + H19/20/21 stack**: same modules fail every run, same point
- Does NOT go through `kryos_panic` (no Rust panic, no diagnostic message)
- Does NOT trigger any of the file-based or stderr-based double-free / use-after-free detectors
- Occurs **before** stage-1 prints `Tokens: N` — so it's mid-tokenize, not in parsing/lowering/codegen
- Is in CODE that stage-0 generated for stage-1 — not in `kryos-rt`

This pattern is consistent with stage-0's Cranelift backend emitting subtly-wrong code for some specific Kryos pattern that appears in the large modules. Most likely candidates:

1. A miscoercion in lex_emit's struct construction (Token has multiple narrow fields; the historical `baff370` fix coerced field widths, but might be incomplete for a specific shape).
2. A bug in cranelift array-of-struct push lowering for some specific element type.
3. An interaction between stage-1's defensive corruption-check in `kryos_array_push` and a specific heap layout that develops after a threshold of allocations.

The next engineer to work on this should start by adding granular printf-style trace inside `lex_emit` / `lex_scan_string` / `lex_scan_token` (the lexer hot path) and narrowing the crash to a specific function call site.

**Caveat on the share-on-clone fix:**

The H8/H19/H20/H21 + H10/H12/H18 stack is **mergeable as diagnostic** but should not ship to production as-is. The leak-on-free behavior means a single `stage-1` invocation accumulates ~100MB. Per-process leak is fine for a CLI compiler invocation (process exits, OS reclaims) but a long-running user process (e.g. an LSP server using Kryos for its analysis) would leak unbounded.

**Production hardening pass needed before merge to main:**

1. Add `ref_count` field to `KryosString` (currently doesn't have one).
2. Add `ref_count` field to `MapHeader`.
3. Replace H10/H12/H18 no-op frees with proper refcounted free.
4. Keep H8/H19/H20/H21 share-on-clone semantics; they're correct given refcounting.

Estimated effort: 1-2 days for the refcount addition + thorough testing.

## Methodology lessons (for the team)

1. **Systematic hypothesis testing beats speculation.** I tested 15 hypotheses today. Most were wrong. Each ruled-out hypothesis was real progress.
2. **Verify the binary actually has your changes.** Cargo `--bin kryos` doesn't rebuild the staticlib. Stat the .lib file's mtime + size between builds. Strings -a as a sanity check on whether your diagnostic strings made it into the linked binary.
3. **Test scripts that swallow stderr silently waste hours.** Every diagnostic surface needs to either be in the test script's output or in a file that survives `abort()` and process exit. `eprintln` alone is not enough on Windows because abort doesn't flush stderr buffers reliably.
4. **Polish under the radar pays compound interest.** The 6 warnings I cleaned up, the README, the test_bootstrap improvement — these save real time on every subsequent cycle and are visible to anyone who reads the repo.
5. **Convergent hypotheses are the real fix.** H8 alone was +0.67 modules. H8 + H19 + H20 was +2 with stable failure set. H8 + H19 + H20 + H21 was +3 with **zero variance**. The right answer was the union of consistent share-everywhere changes, not any single one.
